# Kotlin Multiplatform App Plan

This plan describes the standalone app a future agent should build after the backend API extension is available.
The app repository path is an execution-time input from the user or calling session.

## Product Shape

The app is a compact, real podcast player:

- Android, iOS, and Desktop are first-class targets.
- Shared UI is built with Compose Multiplatform.
- Shared business logic uses Kotlin Multiplatform source sets.
- Platform code owns passkeys, secure storage, audio playback, and app lifecycle integration.
- The backend is the source of truth for subscriptions, indexed episodes, and playback progress.

## Shared Dependencies

Use the current stable versions generated by the Kotlin Multiplatform wizard, then add:

- Compose Multiplatform runtime, foundation, material3, and navigation.
- `kotlinx.serialization-json`.
- `kotlinx.coroutines-core`.
- Ktor Client core, content negotiation, auth, logging, and JSON serialization.
- Ktor engines per platform:
  - Android: OkHttp or CIO.
  - iOS: Darwin.
  - Desktop: CIO.
- SQLDelight runtime and drivers:
  - Android driver.
  - Native driver for iOS.
  - SQLite driver for Desktop.
- Multiplatform settings or a small expect/actual secure storage wrapper for non-secret preferences.

Keep tokens out of SQLDelight. Store tokens only through the platform `SecureTokenStore`.

## Networking

Create one shared `ApiClient` around Ktor Client:

- Base URL is user-configurable for development and defaults to the production API URL chosen by the product owner.
- Install JSON content negotiation with `ignoreUnknownKeys = true`.
- Add bearer auth through an `AuthRepository` that can refresh tokens.
- On `401`, attempt one refresh using the stored refresh token, retry the original request once, and route to signed-out
  state if refresh fails.
- Set `Cache-Control: no-store` expectations for auth responses, but do not rely on HTTP caching for app state.
- Wrap errors in `ApiResult` with status code and backend `ErrorResponse.message`.

Repository responsibilities:

- `AuthRepository`: passkey signup, passkey sign-in, refresh, logout, session state.
- `FeedRepository`: list, add, update, delete, import OPML if the app exposes it later, sync feed.
- `EpisodeRepository`: list episodes, get detail, update progress.

## Local Persistence

Use SQLDelight for app cache:

```sql
CREATE TABLE feeds (
    nano_id TEXT NOT NULL PRIMARY KEY,
    server_id TEXT NOT NULL,
    title TEXT NOT NULL,
    url TEXT NOT NULL,
    synchronized_at TEXT
);

CREATE TABLE episodes (
    id TEXT NOT NULL PRIMARY KEY,
    feed_nano_id TEXT NOT NULL REFERENCES feeds(nano_id) ON DELETE CASCADE,
    feed_title TEXT NOT NULL,
    guid TEXT NOT NULL,
    title TEXT NOT NULL,
    description TEXT,
    media_url TEXT NOT NULL,
    media_type TEXT,
    duration_seconds INTEGER,
    published_at TEXT,
    image_url TEXT,
    progress_position_seconds INTEGER,
    progress_duration_seconds INTEGER,
    progress_completed INTEGER NOT NULL DEFAULT 0,
    progress_updated_at TEXT
);
```

Cache rules:

- Replace the feed cache after a successful feed list request.
- Upsert episode rows after list/detail requests.
- Optimistically update progress locally, then push to the server.
- If server progress is newer than local optimistic state, server wins.
- Clear all cached feeds, episodes, and non-secret settings on logout.

## Secure Token Storage

Define shared interfaces:

```kotlin
interface TokenStore {
    suspend fun read(): AuthSession?
    suspend fun write(session: AuthSession)
    suspend fun clear()
}

data class AuthSession(
    val accessToken: String,
    val refreshToken: String,
    val tokenType: String,
    val expiresAtEpochSeconds: Long,
)
```

Platform implementations:

- Android: Android Keystore-backed encrypted storage, such as EncryptedSharedPreferences or DataStore protected by a
  Keystore key.
- iOS: Keychain.
- Desktop: OS credential store when available; otherwise an encrypted local file using a key kept in the user's OS
  keychain/keyring. Do not store raw tokens in plain preferences.

## Passkey Flows

Define shared interface:

```kotlin
interface PasskeyAuthenticator {
    suspend fun createCredential(optionsJson: String): String
    suspend fun getCredential(optionsJson: String): String
}
```

Signup:

1. User enters email.
2. App calls `POST /api/auth/passkeys/signup/options`.
3. Platform `PasskeyAuthenticator.createCredential` creates a credential from returned WebAuthn JSON.
4. App sends credential JSON to `POST /api/auth/passkeys/signup/finish`.
5. App stores the returned token pair and enters the signed-in state.

Sign-in:

1. User enters email or chooses passwordless sign-in without email when the UI supports discoverable credentials.
2. App calls `POST /api/auth/passkeys/authentication/options`.
3. Platform `PasskeyAuthenticator.getCredential` gets an assertion.
4. App sends assertion JSON to `POST /api/auth/passkeys/authentication/finish`.
5. App stores the returned token pair and enters the signed-in state.

Platform notes:

- Android: use Credential Manager passkey APIs.
- iOS: use AuthenticationServices public-private key credential APIs.
- Desktop: use a browser WebAuthn bridge served from an allowed relying-party origin, then return the credential JSON
  to the desktop app through a loopback callback. The loopback listener must bind to localhost only and use a one-time
  state value.

## Playback

Define shared player control interfaces:

```kotlin
interface AudioPlayer {
    val state: StateFlow<PlaybackState>
    suspend fun load(episode: Episode, startPositionSeconds: Long)
    suspend fun play()
    suspend fun pause()
    suspend fun seekTo(positionSeconds: Long)
    suspend fun stop()
}
```

Platform implementations:

- Android: Media3 ExoPlayer with foreground/media-session integration.
- iOS: AVPlayer with background audio mode when enabled by the app.
- Desktop: JavaFX MediaPlayer or another JVM desktop audio implementation that supports remote media URLs.

Progress sync:

- Save progress every 15 seconds while playing.
- Save on pause.
- Save after seek once playback stabilizes.
- Save on completion with `completed=true`.
- Save when the app backgrounds or exits if platform lifecycle allows it.
- On episode open, resume from server progress when present; otherwise start at 0.
- When local unsynced progress exists, compare timestamps and send it before loading server state.

## UI Screens

Use Compose Navigation with these routes:

| Route | Purpose |
| --- | --- |
| `auth` | Email entry, passkey signup, passkey sign-in, auth errors. |
| `subscriptions` | Feed list, add feed, delete feed, manual sync. |
| `episodes?feedNanoId={id}` | Episode list for all feeds or one feed. |
| `episode/{episodeId}` | Detail and full player controls. |
| `settings` | API base URL in debug builds, passkey list shortcut, logout. |

Initial state:

- If `TokenStore.read()` returns no session, show `auth`.
- If a session exists, attempt refresh when expired or near expiry.
- After a valid session is available, load feeds and show `subscriptions`.

Primary workflows:

- New user signs up with passkey.
- Returning user signs in with passkey.
- User adds a feed URL.
- App syncs the feed and shows episodes.
- User starts playback.
- User pauses halfway and sees progress persist.
- User signs in on another target and resumes from the synced position.

## Desktop WebAuthn Bridge

Desktop passkeys need a browser because WebAuthn is origin-bound and desktop JVM apps do not share one native passkey
API across operating systems.

Required flow:

1. Desktop app starts a localhost callback server bound to `127.0.0.1` on a random free port.
2. Desktop app creates a one-time `state` value.
3. Desktop app opens the browser to an API-owned WebAuthn bridge page on an allowed origin, passing the callback URL
   and state.
4. Bridge page calls the relevant API options endpoint, invokes browser WebAuthn, then posts credential JSON to the
   localhost callback with the state.
5. Desktop app verifies state, finishes signup/sign-in through the API, stores tokens, and closes the callback server.

If the backend does not serve frontend assets, host this bridge as a tiny static web app on the same relying-party origin
used by passkey config. Update `passkey.allowedOrigins` and CORS explicitly for that origin.
